三、内存泄漏

已修复单例持有 Activity Context
LocalAudioPlayer 是单例（生命周期等同进程），却直接保存传入的 context； 调用方 LocalAudioScreen.kt:148 传的是 LocalContext.current（即 Activity）， 导致每次进入本地音频页都有一个 Activity 被永久钉住。已改为取 applicationContext。 其余 3 个单例（ListeningDiaryManager / BluetoothHeadsetManager / RadioPlayer）经查均已正确使用，无需改动。
audio/LocalAudioPlayer.kt:242, 323
特别处理TomatoTimerView 不能简单套用 applicationContext
此处注释明确写着是有意为之：需要保留 LocalContext 的语言包装， 使后台通知显示应用内语言而非系统语言。若直接改成 applicationContext， 会静默破坏应用内语言切换功能。
正确解法：复用项目里已有的 LanguageManager.createLocalizedContext(ctx, getCurrentLanguage(ctx))—— 它内部正是 applicationContext.createConfigurationContext(appConfig)， 既拿到应用语言、又不持有 Activity，两全其美，无需自己造轮子。
ui/settings/TomatoTimerView.kt:92

四、性能优化

已修复两处 500ms 轮询改为订阅 StateFlow
原实现每 500ms 遍历整个音频列表重建集合。其中 StarSkySimpleContent 的 playingSounds 是 SnapshotStateList，clear()+addAll() 属于两次结构变更， 会无条件触发重组——即便整夜播放状态毫无变化，屏幕常亮时持续耗电。 现已改为订阅 AudioManager.remotePlayingStates 并加 distinctUntilChanged： 状态不变时既不计算也不重组，且响应无 500ms 延迟。
ui/starsky/StarSkyScreen.kt:256 ｜ ui/starsky/StarSkySimpleContent.kt:87
兼容性：点击卡片时的乐观更新仍然有效——流是真实状态的权威来源， 与原实现"每 500ms 用真实状态覆盖一次"在语义上等价。
已修复组合期磁盘扫描改为内存索引
getCachedFile() 原本每次调用都执行 cacheDir.listFiles() 全目录遍历， 而它在 SoundsScreenContent.kt:281 处没有 remember 包裹——每次重组都扫一遍磁盘。 已改为正缓存（ConcurrentHashMap）+ 负缓存（KeySet）双结构，并在 download 成功 / deleteCache / clearCache 处同步维护，保证索引与磁盘一致。
audio/AudioCacheManager.kt:70
已修复冷启动避免两次 58KB 全量 JSON 解析
initializeDefaultManifest() 在 MainActivity.onCreate 主线程调用， 原本会对 assets 与缓存各做一次 gson.fromJson 全量解析（构造数百个 SoundMetadata）。 新增 peekManifestSignature()，用 JsonReader 流式只读取 version 与 sounds 数量， 版本一致时（绝大多数启动）完全跳过全量解析，仅在真正需要更新时才解析并写盘。
audio/AudioResourceManager.kt:51
为何没有改成异步：getCachedManifest() 依赖 loadPersistedManifest() 兜底， 异步化会让"首次安装 + 无网络"时空星页拿到 null 而显示空白—— 竞态风险明显大于这几十毫秒的收益，故保持同步调用、只优化解析开销。
